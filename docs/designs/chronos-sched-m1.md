## Problem Statement

Debugging distributed workflow executions today means grepping thousands of disconnected worker logs after a failure has already overwritten or lost intermediate state. Meanwhile, the durable-execution ecosystem splits in two:

- Distributed schedulers (**Temporal**, **Restate**, **River**, **Dagu**) treat the event journal as internal crash-recovery plumbing behind a server or basic web UI.
- Time-travel checkpointing and state branching (**LangGraph**, **Kitaru**) live inside single-process Python agent frameworks, not distributed multi-worker Go systems.

**ChronosSched** bridges that gap as a single, self-contained Go binary that pairs distributed multi-worker DAG scheduling with an interactive execution flight recorder: every workflow run has an immutable event journal, live crash recovery, deterministic side-effect-free replay, and Git-style timeline branching (`fork` and `diff`).

## What Makes This Cool

Within 30 seconds of installing one binary (zero Postgres, Redis, or Kafka required), any engineer can run:

```bash
chronos demo --workers 5
```

ChronosSched uses a default 100-task demo workflow embedded inside the binary via `//go:embed` (with `--workflow <path>` supported as an optional override), spawns five real worker OS processes, initializes an embedded SQLite WAL event journal, and opens a live Bubble Tea terminal inspector:

```text
+----------------------------------------------------------------------+
| CHRONOS - Workflow Inspector  [run_001 | branch: main | RUNNING]     |
+----------------------------------------------------------------------+
| Workers: 5/5 alive   Tasks: 34/100 done   Leases: 5 active           |
+------------------------------------+---------------------------------+
| DAG Execution                      | Event Journal (seq 001..042)    |
| [ok]  01 fetch_config     (w-1)    | 038 LEASE_GRANTED task=04 w-3   |
| [ok]  02 parse_schema     (w-2)    | 039 CHECKPOINT_SAVED cp=003     |
| [run] 03 transform_batch  (w-3)    | 040 WORKER_HEARTBEAT w-3 ok       |
| [run] 04 enrich_records   (w-4)    | 041 TASK_STARTED task=04 tok=7  |
| [q]   05 aggregate_out    (wait)   | 042 TASK_COMPLETED task=02      |
+------------------------------------+---------------------------------+
| [k] Kill worker  [r] Replay dry-run  [f] Fork checkpoint  [d] Diff   |
+----------------------------------------------------------------------+
```

The user presses `[k]` to `SIGKILL` a live worker mid-task. ChronosSched detects the missed heartbeat in under 5 seconds, marks the interrupted attempt explicitly (`AMBIGUOUS_OUTCOME`), increments the monotonic fencing token, and reschedules eligible unfinished work to a healthy worker. Then the user selects an earlier checkpoint, overrides an input payload, forks an isolated timeline (`run_002`), and compares both timelines side-by-side (`chronos diff run_001 run_002`) without mutating `run_001`.

### Target M1 CLI Surface

```bash
chronos init                                          # Create .chronos/ journal dir, config.yaml, and starter demo.yaml
chronos demo --workers 5 [--workflow demo.yaml]       # Self-contained 5-worker demo using embedded 100-task workflow
chronos server start                                  # Start coordinator process + RPC endpoint
chronos worker start --concurrency 8                  # Start standalone worker process
chronos workflow run pipeline.yaml                    # Submit workflow via coordinator RPC
chronos workflow inspect run_001 --live               # Live read-only TUI attached to coordinator RPC
chronos history run_001                               # Inspect event journal (offline SQLite read or RPC)
chronos replay run_001 --dry-run                      # Side-effect-free deterministic replay (offline SQLite read)
chronos fork run_001 --checkpoint 3 --override task.key=value  # Fork from checkpoint N via coordinator RPC
chronos diff run_001 run_002                          # Compare two timelines (offline SQLite read)
```

## Constraints

- **Language & Engineering Standards (`AGENTS.md`):** Go 1.23+, `gofmt`, `go vet ./...`, `go test -race ./...`, explicit error handling everywhere, deterministic unit tests, no fabricated benchmarks, and ADRs in `docs/adr/` for non-trivial design choices.
- **Single-Binary, Zero External Infra:** Must run on macOS ARM64 and Linux with no mandatory Redis, Kafka, or PostgreSQL. Uses pure-Go embedded SQLite (`modernc.org/sqlite`) in WAL mode for M1 durability.
- **Honest Execution Guarantees:**
  - **At-least-once task execution**, guarded by idempotency keys and monotonic fencing tokens (`lease_epoch`).
  - Durable event persistence (SQLite WAL commit) before acknowledging state transitions.
  - Deterministic replay reconstructs scheduling and state transitions from recorded events without re-executing external side effects.
  - Explicit `AMBIGUOUS_OUTCOME` state recorded when a worker dies mid-lease before reporting completion.
  - No claim of exactly-once external side effects without destination cooperation.
- **Standalone Ecosystem Boundary:** ChronosSched owns distributed task scheduling and durable workflow orchestration only. It must remain independently usable without installing Daktari Core, Boxlet, EdgeGate, Keelway, IoRa, TraceMesh, FlashStore, GPU-Arena, or VektorDist.
- **Explicit M1 Non-Goals (Deferred):** Distributed consensus / multi-coordinator HA (Milestone 2), multi-branch merge / advanced branching topologies (Milestone 2), multi-tenant `org_id` control plane (Defer), Kubernetes orchestration (Defer), production web dashboard (Defer), GPU-specific scheduling (Defer).

## Premises

1. **Flight-recorder + basic `fork` & `diff` belong in Milestone 1:** Landscape search confirmed Restate owns single-binary durable execution and Dagu owns single-binary Go YAML DAGs. Pulling reference-by-lineage (copy-on-write) checkpoint forking (`parent_run_id` + `fork_from_seq` + payload override) and `chronos diff` into M1 delivers the full 30-second demo differentiator and avoids a schema rewrite in M2.
2. **Embedded SQLite WAL, not a custom database:** Using `modernc.org/sqlite` behind a `JournalStore` interface keeps M1 focused on scheduler correctness while preserving a clean swap path to FlashStore or replicated storage in M2.
3. **Honest at-least-once semantics with fencing tokens:** Worker crashes during a lease produce an explicit `AMBIGUOUS_OUTCOME` event and bump the task fencing token before reassignment, preventing zombie workers from committing stale completions.
4. **One clean workflow authoring surface in M1:** M1 defines DAGs in YAML backed by Go-registered task handlers (plus built-in deterministic demo tasks), rather than maintaining two full workflow DSLs simultaneously before the core engine stabilizes.
5. **Real OS worker processes + clean binary distribution:** `chronos demo` spawns real worker subprocesses (not fake goroutines) so `SIGKILL` recovery is real, and the binary ships via `go install` and GitHub Releases (GoReleaser) after initializing the local git repository.

## Approaches Considered

### Approach A: Minimal Viable (SQLite WAL Coordinator + HTTP/JSON Workers + Bubble Tea TUI)
- **Summary:** Flat Go service coupling scheduler transitions directly to SQLite transactions with a simple JSON-over-HTTP worker protocol.
- **Effort:** S (human: ~1 week / AI-assisted: ~2-3 hours) | **Risk:** Low.
- **Why not chosen:** Coupling scheduler state transitions to SQLite I/O slows deterministic fault-injection testing and forces a refactor before Milestone 2 consensus or FlashStore integration.

### Approach B: Deterministic Core + Pluggable JournalStore (SQLite WAL) + Real Multi-Process Workers & TUI (Selected)
- **Summary:** Pure, clock-injected Go state machine (`pkg/engine`) emitting events and effects, backed by a pluggable `JournalStore` (SQLite WAL in M1), typed coordinator-worker RPC with monotonic fencing tokens, real multi-process workers, and a Bubble Tea flight-recorder TUI.
- **Effort:** M (human: ~2-3 weeks / AI-assisted: ~4-6 hours) | **Risk:** Low-Med.

### Approach C: Content-Addressed Merkle-DAG Store ("Literal Git for Workflows")
- **Summary:** Store every checkpoint, input, output, and scheduling decision as SHA-256 content-addressed objects in a `.chronos/` object store with Git-style branch refs.
- **Effort:** L (human: ~3-4 weeks / AI-assisted: ~6-8 hours) | **Risk:** Med-High.
- **Why not chosen:** Building a crash-safe object store + ref locking + lease store from scratch duplicates FlashStore and risks spending M1 debugging custom storage instead of scheduler correctness and recovery semantics.

## Recommended Approach

Build **Approach B: Deterministic Core + Pluggable `JournalStore` (SQLite WAL) + Real Multi-Process Workers & TUI**.

### Package Architecture

```text
chronos-sched/
├── cmd/chronos/            # Single-binary CLI entrypoint (init, demo, server, worker, workflow, history, replay, fork, diff)
├── pkg/core/               # Shared domain types (RunID, TaskID, FencingToken, Event, TaskStatus)
├── pkg/dag/                # YAML workflow parser, cycle/schema validator, topological dependency resolver
├── pkg/engine/             # Pure deterministic state machine: Step(state, cmd, now) -> ([]Event, []Effect) and Fold(events) -> RunState
├── pkg/store/              # JournalStore interface + sqlite/ (pure-Go modernc.org/sqlite WAL implementation)
├── pkg/coordinator/        # Coordinator server, lease reaper (<5s detection), worker registry, fencing enforcement
├── pkg/worker/             # Standalone worker process: heartbeat loop, task executor registry, graceful/abrupt shutdown
└── pkg/tui/                # Bubble Tea live workflow inspector (DAG view, worker table, event journal, kill/replay/fork/diff triggers)
```

### Core Data & Event Model

- **Append-Only Event Journal (`events` table in SQLite WAL):**
  - Columns: `run_id`, `seq` (monotonic per run), `ts_ns`, `event_type`, `task_id`, `attempt`, `fencing_token`, `worker_id`, `payload_json`.
  - **Checkpoints:** Each `CHECKPOINT_SAVED` event carries a monotonic per-run checkpoint number (`cp=1, 2, 3...`) recorded at its event `seq` (for example, `cp=003` at `seq=039`). CLI flag `--checkpoint N` always addresses checkpoint number `N`, which the coordinator resolves to that `CHECKPOINT_SAVED` event's `seq` (`fork_from_seq`).
  - **Timeline Lineage (`runs` table) & Reference-by-Lineage Storage:**
    - Columns: `run_id`, `parent_run_id`, `fork_from_seq`, `workflow_hash`, `overrides_json`, `status`, `created_at`.
    - M1 commits to **reference-by-lineage (true copy-on-write)** storage: `run_002` stores only its own post-fork events (`seq > fork_from_seq`) in `events`, referencing `parent_run_id = run_001` and `fork_from_seq = <resolved seq of cp=N>`. `JournalStore.LoadRunEvents(run_id)` recursively resolves the ancestor prefix chain (`1..fork_from_seq` across single- or multi-hop forks) and returns one unified ordered event stream to `engine.Fold`.
  - **Forking (`chronos fork run_001 --checkpoint N --override task.key=value`):**
    - Resolves checkpoint `N` to `fork_from_seq`, creates `run_002`, and appends `TIMELINE_FORKED` carrying the payload override.
    - **In-flight task handling in `pkg/engine`:** Any task that was `LEASED` or `RUNNING` (not yet `COMPLETED`) at `fork_from_seq` has its inherited lease cleared on `run_002` and is re-enqueued as `PENDING` so it will be dispatched with a fresh fencing token.
    - **Upstream override validation:** Any `--override task.key=value` targeting a task already `COMPLETED` at `<= fork_from_seq` is rejected with a validation error (users fork at an earlier checkpoint prior to that task's completion so upstream memoized outputs remain sound). Upstream completed tasks (`<= fork_from_seq`) stay satisfied from recorded outputs; downstream tasks execute fresh on `run_002` without mutating `run_001`.
  - **Diffing (`chronos diff run_001 run_002`):** Walks `parent_run_id`/`fork_from_seq` lineage to find the lowest common ancestor, reconstructs both runs via `JournalStore.LoadRunEvents` + `engine.Fold`, and prints diverging events, task outcomes, retries, and timing deltas.
- **Lease & Fencing Protocol:**
  - Every task dispatch grants a lease `(task_id, attempt, worker_id, fencing_token, expires_at)` persisted atomically with `TASK_LEASED`.
  - Workers send periodic heartbeats (e.g., every 1s; lease TTL 3-4s so failure detection stays under 5s).
  - If a lease expires before completion, the coordinator appends `LEASE_EXPIRED` + `TASK_OUTCOME_AMBIGUOUS`, increments the fencing token, and re-enqueues the task per retry policy. Any late completion arriving with a stale `fencing_token` is rejected with `STALE_FENCING_TOKEN`.
- **Coordinator Crash & Restart Recovery:**
  - On startup, `pkg/coordinator` loads all non-terminal runs (`RUNNING`, `PAUSED`) from `JournalStore` and reconstructs each run's in-memory scheduler state via `engine.Fold`.
  - Active leases persisted before coordinator downtime enter a bounded startup grace window (one lease TTL from coordinator start, capped under 5s) so surviving workers can reconnect and renew active leases; unrenewed leases expire after the grace window with `LEASE_EXPIRED` + `TASK_OUTCOME_AMBIGUOUS` and are rescheduled.
  - Surviving workers retry coordinator registration and heartbeats with bounded backoff, presenting their `worker_id` and active `(task_id, fencing_token)` leases on reconnect.
- **CLI Transport vs Offline Read Boundary & TUI Controls:**
  - **Coordinator RPC required (single-writer path):** `workflow run`, `workflow inspect --live`, and `fork` route through the running coordinator RPC endpoint to avoid SQLite write contention and keep in-memory scheduler state authoritative.
  - **Offline direct SQLite WAL read (read-only):** `history`, `replay`, and `diff` open the SQLite WAL journal in read-only mode when no coordinator is running (and also work while the coordinator is running).
  - **Local lifecycle commands:** `init` creates `.chronos/` (journal DB, default `config.yaml`, starter `demo.yaml`), `demo` runs an embedded coordinator plus local child worker processes, and `server start` / `worker start` run standalone processes.
  - **TUI `[k] Kill worker` scope:** In `chronos demo`, `[k]` sends `SIGKILL` directly to a local spawned child worker PID. In `chronos workflow inspect --live` against external workers, `[k]` is disabled (read-only live inspector).
- **Deterministic Replay (`chronos replay run_001 --dry-run`):**
  - Reads the recorded event log via `JournalStore.LoadRunEvents` and feeds it through `engine.Fold` (and re-verifies every scheduling decision against `engine.Step`), proving 100% state reconstruction consistency without invoking any task executors or external side effects.

Question D2:
D2 - Choose the Coordinator-Worker and CLI RPC transport protocol for M1
Project/branch/task: chronos-sched (docs/designs/chronos-sched-m1.md:148; Architecture Review, R1).
ELI10: Your coordinator needs to talk to 3-5 worker processes (task dispatch, 1-second heartbeats, completions) and stream live events to the Bubble Tea terminal inspector. We can build this with Go's built-in `net/http` + JSON + Server-Sent Events (SSE) with zero code generation, or bring in ConnectRPC + Protobuf with `.proto` schemas and a `buf` generation pipeline.
Stakes if we pick wrong: Protobuf adds build-pipeline friction for contributors in M1 if you don't need polyglot workers yet, while raw HTTP/JSON means writing request/response structs manually in Go instead of generating them from a `.proto` contract.
Recommendation: A) Go stdlib `net/http` + typed JSON + SSE because M1 is Go-only, SSE gives clean real-time streaming to the TUI with zero extra dependencies, and you can inspect every RPC with `curl` while keeping wire structs isolated inside `internal/runtime`.
Note: options differ in kind, not coverage - no completeness score.
Pros / cons:
A) Go stdlib net/http + typed JSON + SSE (recommended) [Effort: S (human: ~2 days / AI-assisted: ~20 min) | Risk: Low]
  ✅ Zero external codegen tools (`buf`/`protoc`) so `go test ./...` and `go install` work out of the box for any Go contributor.
  ✅ SSE (`text/event-stream`) streams live journal events to `workflow inspect --live` and `demo` cleanly over standard HTTP/1.1 or HTTP/2.
  ❌ No cross-language `.proto` contract generated automatically if you add Rust or Python workers in Milestone 2.
B) ConnectRPC + Protobuf [Effort: M (human: ~4 days / AI-assisted: ~45 min) | Risk: Low-Med]

### Section 4: Performance Review
- **SQLite WAL write path:** Single-writer pool (`MaxOpenConns(1)`) + `_txlock=immediate` + `_synchronous=NORMAL` eliminates `SQLITE_BUSY` retries on the hot dispatch/completion path. Batching `TASK_COMPLETED` + `CHECKPOINT_SAVED` into one transaction halves WAL commits per task (~200 writes total for a 100-task DAG, well under ~1-2ms/tx on local SSD).
- **Indexes required (`internal/store/sqlite`):**
  - `PRIMARY KEY (run_id, seq)` on `events` (covers `LoadRunEvents` prefix scan without table scan).
  - `INDEX idx_events_run_cp ON events(run_id, event_type, seq)` (covers checkpoint lookup without scanning full run history).
  - `INDEX idx_runs_status ON runs(status)` (covers coordinator startup reload of non-terminal runs).
- **Bounded memory & HTTP timeouts:** Every HTTP client/server call uses explicit `context.WithTimeout` (RPC deadline `5s`, strictly greater than SQLite `_busy_timeout=2000ms`). SSE live subscribers use bounded per-client channels (e.g., buffer 256) with slow-consumer drop/resync so a stalled TUI never blocks the coordinator scheduling loop.
- **Scale & benchmarks:** Provisional targets (<5ms p95 local scheduling overhead, <5s failure detection, 100+ concurrent tasks) remain `[estimated]` until measured by `go test -bench` in `T6`.
- **Findings:** 0 unresolved performance blockers (`R2` and `R5` approved).
